# Canon CRG-064 / CRG-064H: SEO repair, 27 November 2026

Baseline: `502f1029b6b82c4995f34981ab7fe807694781b5` on `main`.

Renovated toner details published `NewCondition` in the Offer schema. Their
canonical `product_type_key=renovated` now produces `RefurbishedCondition`;
original and newly manufactured compatible products retain `NewCondition`.
This also covers renovated HATONA products and renovated sets.

Product snippets previously cut the combined description at 158 characters,
sometimes ending at a printer series or a colour label without its capacity.
The Woo `metadescription` now survives catalog mapping and is used when it is
clean and within the existing 35–158 character contract. The fallback adds
whole facts and whole printer identifiers only when they fit. It does not
truncate a printer identifier or partially publish a CMYK capacity statement.

The catalog changes were made separately in WooCommerce: 32 existing cards,
five corrected sales photographs, existing image metadata, and two explicitly
approved HATONA CMYK sets. Product content remains shop-neutral. No forced
catalog sync, product-list filtering, AI recommendation policy, cart or checkout
change is included in this commit. HATONA sets remain optional under the
catalog rules; these two were individually approved.

## Verification

The same public 7,750-product regression fixture, dated 17 November 2026, was
used on both versions. It is not represented as the current live inventory.
No orders, customer data or credentials were copied into the checkout.

| Command | Baseline | Final |
| --- | --- | --- |
| `npm run check` | pass, 25.833 s | pass, 26.323 s |
| `npm test` | pass, 96.796 s | pass, 96.021 s |
| `npm run build` | pass, 14.561 s | pass, 12.817 s |

Six new regression tests exercise the actual mapping, snippet and JSON-LD
functions. They cover canonical condition semantics, renovated singles and
sets, whole printer names, long per-colour capacities, Woo metadata retention,
and unsafe/oversized metadata fallback. They are included in both `test:seo`
and the offline build release guard. Existing functionality and security suites
passed.

An alternating, same-process CPU benchmark formatted the same 7,750 products
nine times per version: median 310.548 ms before and 283.035 ms after. This
measures formatting work only; it does not measure network response time,
mobile Lighthouse, or the customer's time to a usable page. The repair changes
server metadata rather than the interactive purchase flow. No claim of a
measured live latency improvement is made.

## Publication and rollback

At preparation, the repository base was still the current `main` head. The
tested files are published together as one commit; unrelated files and catalog
fixtures are excluded. A production deployment is required for the frontend
repair, and a natural nightly catalog update is required for the Woo changes
to reach ToneryMaxim. Neither is claimed complete merely because tests pass.

After deployment, check a renovated single, a renovated set and an original
product: Offer condition, complete description meta tag, canonical URL,
existing price and availability. Preserve the normal nightly product sync.
Rollback is a normal revert of this repair commit, followed by deployment.
The separate Woo backup CSV restores the 32 original card fields; newly
created sets can be moved to draft without permanent deletion.
